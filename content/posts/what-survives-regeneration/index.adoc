[.lead]
Aden regenerates the link:/glossary/#_knowledge_graph[knowledge graph] from source. Every call to `aden gen` re-parses every file and rebuilds every node. Anything written into generated output is overwritten. This is correct behavior. A graph that preserved stale generated content would accumulate link:/glossary/#_drift[drift]. But it creates a problem for intent: the human context and agent reasoning that accumulates alongside a symbol cannot be reconstructed from the source by any parser, and overwriting it on every regeneration means the graph has no memory.

[NOTE]
.The short version
====
`aden overlay <anchor>` creates a git-tracked `.aden/overlays/<slug>.adoc` file holding `[human]` and `[agent]` intent blocks for a symbol. On each `gen` run, `reconcile_anchor` performs a three-way merge: base is the last generated version, theirs is the newly generated version, ours is the overlay. Human and agent context blocks survive. A collision guard rejects any overlay whose `:anchor:` header does not match the anchor it is being applied to, so a renamed symbol cannot silently carry the wrong intent forward. Context-assembling readers (`asm` and `ask`) fold the overlay into context; topology-only readers (`query`) do not.
====

== The problem with generated files

There is a standard convention for handling generated content: write `DO NOT EDIT: generated by <tool>` at the top of the file. The annotation signals that editing this file is futile; the next generator run overwrites it. The correct approach is to keep your changes in the source (the schema, the grammar, the proto file) and regenerate from there.

This works for generated code. A generated parser, a generated protobuf binding, a generated query layer: these are mechanical output. There is nothing to preserve in the generated file itself that is not already encoded in the source it was generated from.

A knowledge graph node is different. It is generated from source code, but source code does not contain everything worth knowing about a symbol. A function's contract ("this must be called after the connection pool is initialized; it panics if the configuration is absent") might be in a comment. It might be obvious from context to someone who has read the surrounding code. It might be known only to the person who debugged a failure against it two months ago, or to the agent that traced a production incident back to a missing initialization call.

That knowledge is intent. Intent is not the same as documentation. It is the human or agent reasoning about why the symbol works the way it does, what its failure modes are, what the reader building on top of it needs to know. It cannot be recovered by re-running `gen`. If it lives only in the generated output, it is gone the next time the graph is rebuilt.

== Overlays: intent alongside the graph

An overlay is a file in `.aden/overlays/`, named by a slug derived from the anchor, tracked in git.

```bash
$ aden overlay aden://module/aden-index/src/store.rs#cache_load
Wrote .aden/overlays/cache_load.adoc
```

The generated file has a `:anchor:` header (the anchor it was created for) and two content blocks: `[human]` and `[agent]`. Both start empty. You commit this file to version control alongside your code. It lives in the repository, shows up in diffs, is present across every clone, and can be reviewed in a pull request.

When `gen` rebuilds the graph, `reconcile_anchor` runs for every anchor that has a corresponding overlay file:

[.mermaid]
----
flowchart LR
  A["base: last generated version"] --> M["reconcile_anchor\nthree-way merge"]
  B["theirs: newly generated version"] --> M
  C["ours: overlay content\n.aden/overlays/"] --> M
  M --> D["merged node\nin the graph"]
  M --> E["collision guard\nanchor mismatch → reject"]
----

The three-way merge preserves the overlay's intent blocks in the merged result. If the generated content changed (a new caller discovered, a signature refactored), those changes appear in the merged node too. The intent blocks do not compete with the generated content; they augment it. Regeneration does not choose between freshness and memory. It has both.

== The collision guard

link:/glossary/#_anchor[Anchors] are not stable under all refactors. A renamed function gets a new anchor. A symbol moved to a different module gets a new path. An overlay file written for the old anchor would either attach to nothing, or (the worse case) silently attach to a different symbol that happened to inherit the same slug.

The collision guard closes that failure mode: before applying any overlay, `reconcile_anchor` checks that the `:anchor:` header in the overlay file matches the anchor being merged. If it does not match, the overlay is rejected with an explicit error. The symbol is regenerated cleanly, without the mismatched intent, and the user is told that the overlay needs to be updated.

A renamed symbol carries no prior intent forward. The user re-creates the overlay for the new anchor. This is the correct behavior: intent written for one symbol should not appear on a different symbol just because the slug happened to collide.

== Prior art and what is different

The three-way merge is not a new algorithm. Git applies it when merging branches. `diff3` describes it as a formal operation on three text files. The specific structure is standard: base is the common ancestor, theirs is the incoming version, ours is the local modification.

What is different is where the merge is applied. The unit is not a file, but an intent block within a node of a knowledge graph. The merge runs not at commit time but at graph-generation time, inside the pipeline that produces the queryable document. The result: the graph is not a pure function of the source code. It is a function of the source plus the committed intent blocks.

This is the inversion of the `DO NOT EDIT` convention. In the standard pattern, the generated file is the part you do not edit. In overlays, the overlay file is exactly the part you are supposed to edit, and the three-way merge is the mechanism by which those edits survive the part that is regenerated.

== How readers use overlays

Not all readers fold overlay content into their results. The distinction is design, not oversight.

Context-assembling readers (`asm` and `ask`) fold overlays via `fold_overlay`. When they retrieve a symbol's context to assemble an answer, the intent blocks are included in the document the model receives. A question about a symbol gets the generated summary plus the human reasoning and agent notes that have accumulated alongside it.

Topology-only readers (`query`, with its `--backlinks` and `--impact` traversals) stay on the structural graph and do not include overlay content. A link:/glossary/#_blast_radius[blast-radius] report lists what depends on a symbol; it does not need the human reasoning about the symbol's contract. A caller graph is topology. The contract is intent. They answer different questions.

`gen --propose` offers a dry-run path: it shows what the three-way merge would produce for each overlay without writing the result, so you can inspect the merge before committing to it. `gen --force-regen` bypasses the merge gate entirely and regenerates clean. Use it when an overlay needs to be rebuilt from scratch rather than merged.

== The broader point

The pattern that runs through Aden's design is that context and structure are different things. The graph models structure: which symbols exist, which call which, which reference which. That structure is derived from source and regenerated from source.

Context is the layer on top: what a symbol means beyond what its signature says, what its failure modes are, what the reader needs to know before using it. That layer cannot be regenerated, because it is not in the source. It is accumulated by the people and agents working with the code.

Overlays are the mechanism by which that accumulation is not thrown away every time the graph is rebuilt. They are git-tracked, diff-visible, and merge-safe. The graph gets to be both fresh and remembering.
