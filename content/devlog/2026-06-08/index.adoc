[.lead]
A design + planning session, not a code-commit one: reshaped aden's project-tree footprint
into a single opt-in `.aden/` (ADR-005, proposed), hardened the `AGENTS.md` guidance-block
editing, reality-checked the "match/surpass the performance leader" target into an execution
roadmap, and corrected a process leak where subagents fell back to `grep` instead of aden.
Then the afternoon became a full build of the interactive graph viewer: `aden viz` (text export)
and `aden view` (offline browser graph: communities, git-history replay, synapse mode). A
graph self-audit surfaced the `EdgeType::Contains` split (Rounds 1-20 below).

== Project-tree footprint & opt-in tracking: ADR-005 (proposed)

The driving complaint: aden taints a project with more than `.aden/`, and even `.aden/` is
committed-by-default, which collides with the repo's own guidance. Verified the contradiction
in our own docs: ADR-003 says *commit durable intent*; `AGENTS.md` says *never commit
`.aden/` (build artifact)*. Both shipped. An implementer can't tell which is true.

Wrote `docs/adr-005-footprint-opt-in-tracking.adoc` (status: proposed; no code until
accepted, per the ADR sidebar rule). Decisions:

* *Only `.aden/` at the root.* Fold `.agent/` → `.aden/agent/`, `.adenignore`/`.adenallow`
  → `.aden/ignore`/`.aden/allow`. Single exception: root `AGENTS.md` (ecosystem-standard,
  other harnesses auto-load it, ADR-004).
* *One config file `.aden/config.toml`*: `[profile]` (was `aden.toml`), `[git].track`,
  `[retrieval].hybrid`, `[defaults]`. Retrieval ranking params stay *hardcoded* (eval-tuned;
  exposing them re-opens the overfitting trap from 06-07).
* *Opt-in tracking, `git.track = false` by default.* Mechanism is a generated
  `.aden/.gitignore` that is *self-contained* (never edits the repo-root `.gitignore`).
  `false` ⇒ a single `*` (folder effectively invisible); `true` ⇒ `*` plus a re-include
  allowlist of durable intent only. This resolves the contradiction by *promotion*:
  "`.aden/` is ignored" becomes the default truth; ADR-003's "intent travels with the repo"
  becomes the opt-in.
* *`aden init` opt-in & selectable:* TTY picker with all destructive options OFF by default;
  flags (`--track/--no-track`, `--agents-file/--no-agents-file`) drive the non-interactive
  path; never prompt without a TTY.
* *Migration preserves already-committed `.aden/`*: detect tracked content and don't silently
  untrack it.

Wired in: ADR-005 row added to `docs/index.adoc`; a `[NOTE]` + Related-Documents pointer added
to ADR-003 marking the commit-by-default decision *superseded in part*. Anchors verified
(`<<adr-005>>` resolves, no orphans). *Left staged for review, not committed.*

== AGENTS.md guidance-block hardening (ADR-005 §5)

Asked the real question: can aden safely insert/replace its `AGENTS.md` section without
deleting people's custom entries? Read `seed_agents_md` (`crates/aden-cli/src/commands/init.rs`):
the happy path is already correct (ADR-004): marker-fenced, replace-only-between-markers,
append if absent, never touch bytes outside. But detection is *brittle and fails toward
duplication*:

* It matches the BEGIN marker as the *full decorated line* (incl. the parenthetical). Any
  future reword stops it recognising older blocks, so it appends a *second* block. Stale aden
  sections accumulate across upgrades. (The exact harm the guest rules exist to prevent.)
* Lone/half-deleted markers aren't handled; duplicates are never collapsed; the write isn't
  atomic.

Recorded the fix as ADR-005 §5: match a *stable sentinel prefix*, detect unbalanced markers,
collapse duplicates to one, write via temp + rename. Plus the body's trailing pointer must
track the `.agent/ → .aden/agent/` relocation.

== Reality-check: execution roadmap (research base)

A "match or surpass the performance leader" target arrived as five items. Verified each against
source before planning. Two were mis-aimed:

* *"150+ vendored grammars":* already exceeded: aden bundles *300+* tree-sitter grammars
  (`README.md`). The real gap is *extraction depth* (~11 langs get deep call-graph), not count.
* *"Index the kernel in 3 minutes":* conflates *cold build* (~24 min on a Linux *subset*,
  per `competitive-position.adoc`) with *warm query latency* (the leader's sub-ms). Different
  problems: cold-build = parallel/quantized embed; warm-query = the deferred daemon.
* *`understand` tool:* already exists (`cmd_understand`, `query.rs:1894`).
* *Visualization:* genuinely missing (only the *linter* knows "mermaid"). Highest leverage;
  it hits the stated adoption blocker (*visibility, not speed*).
* *Persistent default project:* genuinely missing (no `ADEN_PROJECT`/default-project).

Wrote `the research notes/topics/aden-roadmap/execution-plan-match-surpass.adoc`. Extends the
existing capability-gaps/competitive-position docs along the *human-facing/ecosystem* axis, with
three guardrails up front: offline+deterministic stays the default (GPU opt-in only), agent-file
config is opt-in (ADR-005), and LSP-style *resolution* is in-scope while *editing* stays a
non-goal. Match items M1-M6, surpass items (living-docs headline, temporal queries,
orchestration), and a weeks-to-12-month sequence.

== `aden viz` (M1): first slice on a branch (`feat/viz-export`)

Per the roadmap's ★★★★★ item. `aden viz <anchor> [--depth N] [--format mermaid|dot|asciidoc|json]`
renders the *blast-radius* subgraph around a symbol: the same outgoing impact-edge set as
`impact-diff`/`query --impact`, BFS-capped by depth. New `commands/viz.rs` modelled on
`impact_diff.rs`; anchor resolution accepts a bare name (`cmd_understand`) or a full `aden://…`
anchor (unique tail-match, ambiguity errors with samples). Deterministic node ids (sorted),
root highlighted.

*Text-first by design.* The renderer is NOT aden's job. `mermaid` (GitHub/mermaid.js-native),
`dot` (graphviz), `asciidoc` (wraps the mermaid in an asciidoctor-diagram `[mermaid]` block so it
renders inline in the user's existing AsciiDoc pipeline as SVG/PNG), and `json` (the machine seam
for a future interactive/3D viewer, same node/edge ids as the diagram formats). Aden emits
portable *source*; the user picks the renderer and the final format. This keeps the offline +
lean + deterministic moat (no bundled Java/Ruby renderer) while making aden compose with
asciidoctor and anything else.

*The `-j` fix:* the global `-j/--json` flag was a silent no-op for viz (printed mermaid). Now it
aliases `--format json`, so a global flag never lies about what it does.

Validation battery (against the freshly built binary): help + top-level listing; full-anchor and
bare-name resolution; ambiguous-name and missing-symbol errors (both with hints); unknown-format
rejection; *determinism* (byte-identical across runs); *depth monotonicity* (12→40→66 nodes at
depth 1/2/3); leaf symbol (`risk_tier`) → root-only graph; valid JSON via `-j` (parsed back);
regressions clear (`communities`/`impact-diff` unaffected). 6 unit tests + MCP flag-parity green;
clippy clean (lone warning pre-existing in `aden-parse:tree_sitter_common.rs:65`). On branch
`feat/viz-export`, *not committed or pushed*; awaiting review.

*Next on viz:* `--communities` and `--connectivity` modes (reuse `detect_communities`); wire the
`json` format into a viewer later.

Committed the first slice as `d3057ca` on `feat/viz-export` (viz only; ADR-005 docs left
uncommitted for review). *Not pushed.*

== Research-first: visualization design (research base)

Before extending `viz`, ran a research pass (3 parallel read-only agents: two web field-surveys,
one aden-internal dogfooding aden's own MCP tools, not grep) and wrote the findings to
`the research notes/topics/aden-roadmap/viz-design.adoc`. Headlines:

* *The field validates emit-don't-render:* the strongest 2026 code-graph tools emit portable
  formats and leave rendering external. Aden is already aligned; do NOT bundle a renderer.
* *Format by view + scale.* Mermaid's edge cap is a *hard 500* (renderer-side, NOT raisable from
  emitted text; 280 was the old fixed value), so Mermaid is small-embeds-only. Graphviz DOT
  (`cluster_*`) is the right default for mid-size + every community view; JSON is the escape hatch.
* *Reduce before emit is the differentiator:* competitor UIs almost universally fail by rendering
  the whole hairball. Plan: depth default 2 (have it), node cap ~50 with `+N more`, edge cap
  300 soft / 500 hard with Mermaid→DOT→JSON auto-fallback, and community-collapse super-nodes.
* *Aden's graph already exposes* 26 edge types (semantic/code + activation weight), node_type,
  source_span, confidence, `detect_communities`, `get_backlinks`, `neighborhood`. *Gaps* to add
  before a rich viewer: cached degree/centrality, community-id on nodes, edge direction, doc
  summaries.
* *Viewer (later, opt-in):* a vendored, offline Sigma.js + graphology localhost page that is a
  *pure JSON consumer* (no own state, can't drift). Never in the core binary; 3D stays an
  optional toy, not the primary view.

Recommended sequence is in the doc: (1) `--communities`/`--connectivity` + caps now;
(2) enrich the `viz` JSON (community-id, degree); (3) only then decide go/no-go on the viewer.

== `aden viz` modes + a determinism bug caught by dogfooding

Implemented the next viz slice (still on `feat/viz-export`): `viz --mode blast|connectivity|
communities`.

* *`--connectivity`:* BFS in *both* directions over all edge types (callers + callees), each
  edge kept in its true orientation. Dogfood: `cmd_understand` connectivity surfaces `real_main`
  (an *incoming* caller) that the outgoing-only blast view never shows. ✓ deterministic.
* *`--communities`:* whole-graph clusters as Graphviz DOT `cluster_*` boxes (per the research:
  DOT, not Mermaid, for grouping), per-community fill colors, member cap (12) with `+N more`,
  top-12 communities. JSON carries community membership.

*The bug:* dogfooding `--mode communities` showed *non-deterministic* output. Community sizes
shifted run-to-run (`359` vs `362`), even though connectivity (my own BFS) was stable. Root cause
was NOT the viz code: `detect_communities` builds its node list from `graph.node_indices()`, whose
order follows graph construction. `cache.rs` inserts nodes by iterating a `HashMap` (randomized
per process). Louvain is *order-sensitive*, so that leaked non-determinism into the partition. The
module's own doc-comment *claimed* determinism ("processed in NodeIndex order"): true but
insufficient, because NodeIndex order itself isn't canonical.

*The fix* (`crates/aden-graph/src/community.rs`): sort the node list by *anchor* before handing it
to Louvain, a canonical order independent of graph-construction order. Now deterministic across 3+
runs (sizes identical). This also repairs the *existing* `aden communities` command, which had the
same latent bug. Connectivity was immune because it returns an anchor-set + topology (order-free).

Validation: 10 viz unit tests + 4 aden-graph community tests green; MCP flag-parity intact; clippy
clean. Docs updated (`docs/commands.adoc` gains a `viz` section). Determinism is aden's moat:
catching this via dogfooding is the system working as intended. Committed `2b9a478` (viz modes +
determinism fix). Not pushed.

== Design pass: `aden view` browser viewer (research-first, validated)

Before building the browser viewer, wrote the design into the research base
(`the research notes/topics/aden-roadmap/aden-view-design.adoc`) and *validated the load-bearing
fork* (the JS library) with a web research agent rather than guessing. Decisions locked:

* *Architecture:* `aden view <anchor>` reuses `viz`'s slice, emits JSON, *inlines* it into a
  self-contained HTML (`const DATA = {…}`, no runtime `fetch` so it works from `file://`), and
  auto-opens the browser (`xdg-open`/`open`/`start`, no-ops in headless). The core stays
  renderer-free; the page is a *pure JSON consumer*.
* *Library (verified 2026-06-08, jsDelivr/package.json):* vasturiano *`force-graph`* (UMD single
  `<script>`, ~178 KB, MIT, native `{nodes,links}`) as the 2D default; *`3d-force-graph`* (UMD,
  ~1.31 MB with three.js bundled in, MIT) lazily inlined only for `--3d` (the "brain" view). Sigma.js
  rejected (ESM-first, not a clean single-`<script>` drop); Cytoscape (~435 KB) is the fallback.
* *Vendoring:* embed the pinned, sha256-checksummed minified bundle in the binary behind an opt-in
  `view` cargo feature (mirrors `dense`); aden's build never runs npm. *No runtime CDN* (removes the
  supply-chain-at-use risk). User flagged "don't use platforms hacked to fuck": captured a
  supply-chain section: pin + checksum + reputable narrow-surface MIT libs + inert self-contained
  output.
* *Beauty as a goal* (user: "most beautiful thing… and still usable"): dark canvas, community-hued
  nodes (perceptual palette), degree-sized nodes, hover focus-dimming, click to side panel; 2D stays the
  default for *reading*, 3D is the gorgeous exploration mode. One shared visual language.
* *Live "watch" updates* deferred to phase 2 (needs a localhost server: `file://` can't re-fetch;
  overlaps the warm-daemon). MVP is a static snapshot.

No viewer code yet. Design + validated library facts only, per the research-first method. Next:
implement the MVP slice on the branch.

== Round 2: the "visual nightmare" (second screenshot)

A connectivity view of a hub (`cmd_understand`, depth 2) came back a *nightmare*: giant overlapping
blue blobs, hundreds of nodes. Two root causes; both things the research (xref:viz-design) told us
and I'd deferred:

* *No reduce-before-emit caps.* A hub at depth 2 pulls in *hundreds* of nodes. Added `NODE_CAP = 60`
  to `blast_slice`/`connectivity_slice`: closest-first BFS, so the cap keeps the *nearest* reach and
  only introduces a new node while under the cap (edges to already-kept nodes still count, so the
  shown subgraph stays connected). Verified: `cmd_understand`/`FjallStorage::new` connectivity depth 2
  → exactly 60 nodes (was hundreds).
* *Over-aggressive node sizing.* `nodeVal = 1 + degree` made high-degree nodes *enormous* (area ∝
  degree). Clamped: degree views use `1 + min(√deg, 3)` (small, roughly uniform), super-nodes use
  `min(2 + √size, 12)`. Smaller `nodeRelSize`, plus stronger charge (`-140`) and link distance (38) so
  the layout spreads instead of blobbing.

Lesson logged honestly: I shipped the modes before the caps and it bit immediately on a real hub. The
research had flagged exactly this. Caps are not optional polish; they are the feature.

== Round 4: open-in-editor (shipped) + OS-agnostic

Implemented "open in editor": right-click a node (or the panel "open in editor →" link) opens the
symbol's file at its line in the editor. No syscall hijack. A `vscode://file{file}:{line}` URI; the
browser routes the registered scheme to the desktop app.

* *Where the line comes from:* the graph node's own `source_span` is *empty* for symbols (caught
  immediately: 0/14 nodes had it). The spans live in the *store*, same source `impact-diff` uses
  (`grep::load_symbol_spans` → `Span{anchor,start,end}` keyed by file). Switched to that: 13/14 real
  symbols get file+line (synthetic `mod-*` hubs correctly have none).
* *`--editor`* flag (vscode | cursor | vscodium | zed | idea | custom `{file}`/`{line}` template).
* *OS-agnostic, deliberately:* the browser opener already covers Linux (`xdg-open`) / macOS (`open`) /
  Windows (`cmd /C start`); the editor path is normalized URI-ready (forward slashes + leading slash,
  so Windows `C:\x` → `/C:/x`), and `vscode://`-style schemes are cross-platform.

Caught + fixed two issues this round (keeping correctness/clarity a priority): looking for line info
on the wrong struct (graph node vs store span), and judging a generated HTML from a *stale binary*
(clippy doesn't rebuild the bin; rebuilt before trusting the output). Clippy clean (bundled-arg lint
addressed), 10 viz tests green.

Used a subagent (aden-enforced: `mcp__aden__*`, no grep) to draft the benchmarks-as-documentation
research note in parallel while writing the code-coupled docs here.

== Round 6: navigation: clickable neighbours, back-trail, in-graph search

== Round 8: git-history replay: watch the project build itself ⭐

The session's headline. The idea started as "simulate what an LLM is touching" and crystallised into

*The pipeline (all real data):*

== Round 17: the graph audits itself: viewer-driven optimization findings

The viewer stopped being a toy and became a *diagnostic*. Asked "what does the graph show we should
optimise?", analysed the whole-graph payload (degree/fan-in/fan-out, community group-purity,
cross-crate coupling), excluding the synthetic `mod-*` scaffolding that connects to everything by
construction. Findings, evidence-backed:

*Healthy:* communities map cleanly to crates (98% purity on the big ones); cross-crate coupling flows
in proper layered directions (everything → `aden-core`; `aden-cli` → everything). Highest blast-radius
nodes are `aden-core::Error` (fan-in 108) and `Document` (65), expected for core types, but the #1
change-risk points.

*Optimisation candidates:*

* 🔴 *706 redundant mirror edges: `Documents` is inverted `PartOf`.* 100% of `Documents` edges are
  the exact inverse of a `PartOf` edge; ~706 originate from `mod-*` nodes (containment), vs only ~374
  genuine prose→code edges. Source is exact: `generate.rs#link_store_edges` emits a mirrored pair for
  every containment: `(mod-X) --Documents--> symbol` (494) *and* `symbol --PartOf--> (mod-X)` (495),
  plus the project→module pair (603/605). So `Documents` is (a) ~19% of all edges as pure mirrors and
  (b) a *semantic misuse* (a module *contains*, it doesn't *document*) that buries the real code↔prose
  signal 2:1. *But not trivially removable:* `aden-asm/traverse.rs` walks `Direction::Outgoing` ONLY,
  and `ask`'s fallback to `mod-project` traverses project→modules→symbols via exactly those forward
  `Documents` edges. The PartOf inverse can't be followed by an outgoing-only walk. So the "redundancy"
  is partly *load-bearing* for top-down traversal on a one-directional engine. Two candidate fixes:
  (A) remove + make traversal follow incoming `PartOf` (broader semantics change), or (B) introduce a
  new `EdgeType::Contains` for the forward containment edge. That frees `Documents` to mean only real
  prose→code, keeps outgoing top-down traversal, and threads `Contains` through enum/kind/all_edge_types/
  string-maps/validate/activation_weight/asm-priority. *Ran a read-only Workflow* (5 parallel Explore
  agents, one per subsystem: asm, query/routing, check/heal/gen, graph/core, viz/lsp/mcp/store) to audit
  every consumer and produce a decision memo + exact edit list before touching a shared edge type. The
  real doc→code `Documents` (generate.rs:567) and its inverse must be preserved.
* 🟡 *Community detector junk bucket.* `c7` looked like "mcp↔lsp entanglement" (50% purity) but has
  ZERO real edges between them. Louvain just sweeps the small peripheral crates (mcp, lsp, benches)
  into one leftover community. Misleads the viz + any community feature. Fix: don't force-merge
  low-connectivity nodes; leave tiny modules standalone or label low-purity communities "misc".
* 🟡 *`aden-cli` monolith.* `c0` = 242 nodes, 1.4× the next (`aden-parse`, 171); `real_main` fans out
  to 63 calls. Candidate: extract command bodies into library crates so MCP/LSP call them directly
  instead of `aden-mcp/run_aden_command` shelling out.

*Method note:* used `mcp__aden__grep` to locate the edge-emission and consumers (per [[use-aden-to-investigate]]),
and verified the `Documents`==inverse-`PartOf` claim against the live payload (100%, 706/706) before
believing it. Decision memo + implementation pending the workflow audit.

== Round 18: `EdgeType::Contains` split lands (the audited fix)

The workflow audit (5 parallel `Explore` agents + a synthesis memo, 336k subagent tokens, 172s) returned
a clear verdict: *fix (A) plain removal is UNSAFE.* 4/5 subsystems (asm-traverse, query-routing,
graph-core, check-heal-gen) depend on the forward edges with *high* risk. `ask`'s thin-stub
fallback to `mod-project` and intent-routing reach module members by walking those edges *outgoing*
(traversal is `Direction::Outgoing`-only; the `PartOf` inverse is unreachable that way). Only
viz/lsp/mcp/store was clear. So I implemented *fix (B): a new `EdgeType::Contains`* for the forward
containment edge, freeing `Documents` to mean *only* genuine prose→code.

*Deliberate deviation from the memo:* gave `Contains` the *exact* priority (11) and activation weight
(0.5) the forward edges had as `Documents`. This is a *pure type-rename + signal cleanup with zero
traversal-behaviour change*, not the memo's stronger 0.9/priority-4 (which I left for a separate,
deliberate tuning decision). Threaded `Contains` through 11 sites the compiler + audit identified:
enum + `activation_weight` (aden-core), `AdenEdge::kind` + `all_edge_types` + the string→type map +
`build_from_storage` load-list + `validate_typed_edges` code-types (aden-graph), `edge_priority`
(aden-asm), `parse_single_edge_type` + `valid_edge_types` (aden-cli util), the two emit sites
(generate.rs:494,603 only, *567 doc→code left untouched*), and an intent-filter rule in query.rs
("any intent that traversed `Documents` for members must also traverse `Contains`"). The one
*non-compiler-enforced* site (`build_from_storage`'s hardcoded `edge_types` vec) was the real trap
the audit flagged: miss it and Contains edges load as nothing on reload. Caught it.

*Validation (all green):*

* `cargo build --workspace` clean (no missed exhaustive `match` arm, the enum-threading safety net).
* tests: aden-asm 27, aden-graph 30, aden-core 27. All pass.
* regen self-graph → `aden viz --mode graph -j`: `Contains` 728 == `PartOf` 728 (containment mirror);
  *0* `Documents` edges from a non-prose node, *0* `Contains` from a non-`mod-*` node. The signal is
  now clean by construction.
* the behaviour fix (A) would have broken: top-down from `mod-project` @depth2 yields
  `Contains:58, PartOf:59, Documents:1`. Containment reachable outgoing via `Contains`, *and* a real
  doc→code `Documents` edge survives. `aden ask "overview of the aden-cli crate"` routes to the
  `mod-project` fallback and its `Edges:` line now includes `Contains`: assembles real context, not a
  thin stub.
* `aden check .`: all typed edges valid, all doc path refs resolve. `aden heal . --gc`: 0 orphans,
  0 drift, 2413 kept.

*Net:* `Documents` is now a *pure* code↔prose signal (the ~374 real prose edges no longer buried 2:1
under containment), centrality no longer double-counts membership, and the graph the viewer renders is
semantically honest, at zero behavioural cost. Workflow-audited, compiler-enforced, behaviour-verified.
