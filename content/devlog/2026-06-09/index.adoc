== Round 22 (2026-06-09): M6 scoped, benchmark breadth + agent-task-success

Returned to the headline mission (prove aden matches/surpasses the retrieval leader, honestly). Scoped
M6 with a 5-agent research workflow (repo-set · task-success · query-scaling · comparability →
synthesis), ground-truthed against the live harness and verified commands (`understand --budget --json`
exists; `aden bench` does *not*). Full scope:
m6-execution-scope.adoc. Key decisions:

* *Carve, don't boil the ocean.* The threads over-scoped (24 repos, ~4k queries, 5 tasks, a Rust `aden
  bench`). The plan instead is the *smallest end-to-end slice that yields one real, honest number*:
  `gen_queries.py` (commit→single-file) on *kin-openapi* → spot-check → existing `eval_corpus.py` →
  first new-repo Recall@K. ~1 week, no agent harness yet, harness already works.
* *Corpus = ~24 repos, each scoped to a sub-tree* (single-target ground truth stays authorable, mirrors
  the T3 `cli/src` precedent), tagged memo-risk; 3-repo pilot first (rustfmt/Rust, kin-openapi/Go,
  uno/C#, deliberately lower-star to dodge pretraining saturation).
* *Query authoring = commit-message→single touched file* (the real bottleneck; ~2× hand-authoring) with
  a non-negotiable manual spot-check gate whose pass-rate is *published next to the recall*. Hard
  anti-overfit line: the sanity `aden search` may only *flag* weak labels, never auto-delete them. A
  genuine miss must survive into the published miss count (the ADR-005 reverse-fit trap).
* *Agent-task-success = T1 locate / T2 explain / T3 blast-radius*, each mapped to a verified command,
  scored 1.0/0.5/0.0 against human gold, vs baselines B0 no-context + B1 raw-grep. The headline isn't
  just success. It's *success at lower token spend than dumping grep output* (mean context tokens is a
  first-class published number).
* *Runner = `scripts/bench.py` (Python) first*, not a Rust subcommand (zero measurement value, gates the
  first number behind plumbing). Emits JSON + a markdown table with caveats *inline* and
  cold-build/cold-embed/reindex/warm as *separate rows*.
* *Honesty is the product here:* external corpora only, params hardcoded per ADR-005 (never tuned to
  these labels), reproducibility stated as the advantage over CQS's higher-but-unpublished headline.

Next concrete step: build `scripts/gen_queries.py` Stage 1 on kin-openapi and produce the first
external-repo recall table, then show it before anything else.

== Round 23 (2026-06-09): M6 build-first slice, first new-repo number + the gate earns its keep

Built the smallest end-to-end slice from the M6 scope and got a real number. New
`scripts/gen_queries.py` (commit-message → single touched file; reusable `--repo/--scope/--ext/--max`;
never runs aden, so it can't reverse-fit). Cloned `getkin/kin-openapi`, scoped to `openapi3/`.

* *First external-repo number* (BM25, debug bin): 30 auto-generated candidates → *R@1 0.20*, R@20 0.37 (low). *Spot-check, not despair:* searched one miss and found the cause immediately. The query
  _"**Add** content-type wildcard support to validation"_ got swamped by BM25 matching the changelog
  verb "Add" (→ `AddRoute`/`AddOperation`…), and its noun "validation" points at the validator, not the
  touched `content.go`. Auto-cleaning (stripping verbs) *hurt* (lost BM25 signal). The real fix is the
  *manual spot-check gate*: 8 of 30 subjects describe a cross-cutting effect that lives in another file,
  so they were excluded (*73% pass rate, published next to the number*).
* *Validated subset (22 labels): R@1 0.20 → 0.273, R@20 0.37 → 0.50, misses 19 → 11.* The gate is
  *load-bearing*. Raw auto-labels are not publishable; culling 8 noisy ones is a +37%-relative R@1
  swing. Validated BM25 (0.273) lines up with the t3-cli BM25 baseline (0.229). Recorded with caveats
  in `eval-sets/README.md` (`ed25677`).
* *Method finding for the corpus scale-up:* commit-subject labels are ~73% usable on this repo; the
  spot-check is mandatory and the cost is real (~the bottleneck the scope flagged). Worth piloting the
  doc-comment→file secondary source on a repo where it's denser, to see if it yields cleaner queries.

*Then the actual claim: BM25 vs hybrid* (`target/release/aden --features dense` + bge-small, gen re-run
per mode). On the 22 validated labels: *R@1 0.273 → 0.364 (+33% rel), R@5 +43%, R@10 +50%, R@20 0.50 →
0.636, MRR +29%, misses 11 → 8* (`f14ef75`). The dense lift *generalises to a third independent repo*,
consistent with t3-cli (R@1 +62%) and Linux (+35%), exactly the "honest win that widens with
unfamiliarity" story. So the M6 build-first slice is *complete*: a reusable query pipeline, the gate
proven load-bearing, and a real BM25-vs-hybrid number on a new corpus. Per prefs: nothing pushed.

== Round 24 (2026-06-09): M6 pilot complete, 3 repos, 3 languages, one honest pattern

Ran rustfmt (Rust) + uno (C#) through the same pipeline (`f62f32b`). Validated-set BM25 vs hybrid:

* kin-openapi (Go, `openapi3/`): R@1 0.273 → *0.364* (+33%), R@20 0.50 → 0.64
* rustfmt (Rust, `src/`): R@1 0.095 → *0.191* (+100%), R@20 0.24 → 0.29
* uno (C#, `Uno.UI/Controls`): R@1 0.150 → *0.150* (flat), R@20 0.20 → 0.30

*Hybrid ≥ BM25 on all three* (plus t3/Linux). The dense lift reproduces across Go/Rust/C#, strongest
where BM25 is weakest. *The real pilot finding is about the method, not aden:* absolute recall tracks
*corpus/method fit*. The commit→file query method shines on *domain-named* files (kin-openapi:
`schema.go`/`parameter.go` ↔ subjects that name the type) and struggles on *platform/concern-named*
churny ones (uno Controls: platform renderers + ambiguous `.iOS`/`.Android` variants; rustfmt:
behavioural subjects ↔ generic `expr.rs`). uno Controls was a poor sub-tree pick. A logic module
(`DataBinding`) would likely fare better. So *sub-tree selection is a first-class corpus decision*, and
the pilot surfaced it *before* paying for 24 repos, exactly its job. Spot-check pass rates 66–73%
(corpus-dependent, all published next to the numbers).

*M6 status:* the build-first slice + pilot are done and honest. The dense advantage generalises; the
query-authoring method has a known fit-dependence to design around. *Next:* `scripts/bench.py` to emit
the comparable JSON+markdown over the pilot, then scale query-gen across the corpus picking
domain-named sub-trees, then the agent-task-success axis. Nothing pushed.

== Round 25 (2026-06-09): bench.py built, and it caught a gen determinism bug

Built `scripts/bench.py` (`675cc66`): runs the corpus through `eval_corpus.py` for BM25 + hybrid,
times cold build separately, emits a comparable JSON + markdown report (caveats inline, cold/warm
separated, spot-check% + memo-risk per repo). It worked, and the *first thing it did was catch a real
defect*: **`aden gen` is not deterministic.**

Isolated rigorously (the session's verify-before-believing, applied to my own benchmark): two
consecutive BM25 bench runs differ (kin-openapi R@1 0.273 vs 0.318); but `search` is deterministic
(gen-once + eval-3× → byte-identical), and the BM25 sorts already tie-break on anchor. Not cross-mode
store contamination either (fresh-store gens *still* differ). The smoking gun: gen's `Stored aden://…`
lines come out in a *different file order each run* (parallel processing). The indexed *set* is stable,
but per-file aggregate doc lengths / BM25 `avg_doc_length` shift with completion order. Borderline
rankings move ~±0.05 recall. Same class as the 2026-06-08 `detect_communities` sort-for-determinism fix.
Full diagnosis + the focused fix (canonicalise entry/symbol order before building the index; regression
test on index stats) in gen-determinism-defect.adoc.

*This is the benchmark earning its keep:* the highest-value thing eval infra can do is find a
correctness bug, and it found one on day one. `bench.py` + `eval-sets/README` now carry a ±0.05 caveat;
the BM25→hybrid *gap* is robust to the wobble, the absolute decimals are not. *Next, high-value +
bounded:* the gen-determinism fix, then re-run the pilot for stable numbers, then the agent-task-
success axis. Nothing pushed.

== Round 26 (2026-06-09): gen-determinism, 2 of 3 causes fixed (diff the cache, not the source)

Fixed the gen non-determinism `bench.py` found (`2b7554f`). The breakthrough was *diffing the
serialized `index-cache.json`* between two clean gens instead of guessing (and, per the user's nudge,
using aden's own `list`/`search` + the cache diff rather than blind grep). Three causes:
(1) `collect_store_entries` used `HashMap::into_values()`, fixed by sorting `(anchor, source_file)`;
(2) *the dominant one*: the indexed contract text carried a wall-clock `:last-verified:` *timestamp*,
so every gen tokenised a different date into the postings (2126/2138 docs differed); fixed by
`index_text()` stripping volatile metadata before indexing (stays in the store, out of the index);
(3) `ingest` dedup ("first wins") order-sensitivity, fixed by sorting `parsed`. Index now byte-identical
*except* a tiny residual: `doc_lengths` differs for ~2/2138 anchors, `avg_doc_length` by ~0.005.
*Residual root (separate, documented):* basename-anchor collisions. `openapi2/helpers.go#copyURI` and
`openapi3/helpers.go#copyURI` share an anchor; the store is anchor-keyed, so gen's parallel writes pick
the survivor last-write-wins. Needs deterministic collision-resolution in gen Phase 1 or dir-qualified
anchors (research note has both). Recall wobble now ~±0.02 (was ±0.05); R@1/R@20 largely stable. 103
aden-index tests green; nothing pushed. *Process win:* two false starts before the cache-diff pinned it.
Verify the artifact, don't theorise.

== Round 27 (2026-06-09): gen+search determinism FULLY fixed (5 causes)

Closed the determinism chain. After fixing gen's index *stats* (Round 26), recall STILL wobbled ±1
rank. The paradox (identical `doc_lengths`/`avg`/posting-sets, different recall) proved it wasn't
gen at all. Traced via the per-query diff to two borderline queries flipping by one rank, then to the
last non-deterministic field: `emit_document` iterated `doc.attributes` (a HashMap) in arbitrary order.
That text is what the index *tokenises*, so unstable order perturbed tokenisation enough to flip a
near-tie. *Fix (`9da0bcf`):* sort attributes (and block attributes) by key. *Result: retrieval is now
fully deterministic*: 5 fresh gens of kin-openapi give byte-identical recall (R@1 0.2727, R@5 0.3182,
R@20 0.4545, MRR 0.3055); rustfmt likewise. (Cache *file* bytes still vary (serde HashMap key order),
but the data + recall are identical; cosmetic.)

*Full chain (all fixed):* (1) wall-clock `:last-verified:` in indexed text; (2) `HashMap::into_values`
in `collect_store_entries`; (3) order-sensitive `ingest` dedup; (4) parallel store-write anchor-collision
race; (5) `emit_document` attribute order. The benchmark `bench.py` built earlier did its job end-to-end:
found a real correctness bug and drove it to a full fix. 103 aden-index + emit/cli tests green.

*Canonical numbers (`2cf9fa7`):* re-ran the pilot via `bench.py` on the deterministic build. Recall is
now byte-stable (5 fresh gens identical), so these are reproducible, not ±0.05 noise:
kin-openapi (Go) BM25 R@1 0.273 / Hybrid 0.409 (+50%); rustfmt (Rust) BM25 R@5 0.143 / Hybrid 0.238
(+67%); uno (C#) BM25 R@20 0.150 / Hybrid 0.300 (+100%). *Hybrid ≥ BM25 on all three.* The dense lift
reproduces across Go/Rust/C#. Stale "±0.05 / not deterministic" caveat replaced everywhere with the
deterministic-as-of-9da0bcf statement. Nothing pushed.

== Round 36 (2026-06-09): ask density/immediacy work COMMITTED

The Round-35 WIP landed as `6d20c6b` (23:06; 876 insertions incl. the harness), structured as three
fix layers:

* *F1: render fixes* (`traverse.rs`): signature tables get a doc-title fallback name (the absent
  Name row made every signature render to *nothing*); the leading docstring paragraph and the
  signature table are exempt from intent block-filters (a List/Usage filter was deleting the only
  substantive prose a code node has); callee tables capped at `MAX_CALLEES=12` so hub nodes stop
  burning the budget on call-graph scaffolding; embedded newlines stripped from table cells;
  truncated nodes charge their cost before the budget break.
* *F2: budget-aware source hydration* (`traverse.rs`/`cache.rs`): when summaries leave most of the
  budget unspent, `hydrate_root` packs included nodes with their *actual source lines*,
  `source_hash`-verified (stale store → a note, never stale source), per-node caps, deterministic
  BFS order. Callers fold in as a depth-1 frontier (incoming `Calls`/`Uses`, reversed in the
  ephemeral graph, since outgoing-only traversal starved at leaves); the hub check is degree-gated
  (`HUB_DEGREE_CAP=32`) so a real symbol in a small crate's `lib.rs` isn't mistaken for an index node.
* *F3: escalation ladder* (`query.rs`/`cmd_ask`): three non-anchor-changing rungs for an underfull
  anchor: (a) re-render without the intent filter, (b) fold callers, (c) depth +1, *before*
  community broadening, which now packs members by *BM25 query-relevance, not degree* (the degree
  pick was re-creating M14's hub-over-leaf bias at the fallback layer) and never fires for an
  explicit `--from`. The routed anchor always stays primary and the summary stays truthful.

Plus `scripts/eval_ask_density.py` (15-case end-to-end eval with the Round-35 gates). The commit
message doesn't record a gate run. *Verifying the gates green is the open follow-up.* main is now
ahead 8 / behind 3 of origin.
